# PixelVeil — DECISIONS.md

Record of significant decisions and why they were made — so reasoning doesn't get relitigated mid-build or forgotten later.

---

### D1 — Build a post-processing tool, not a live/in-recording redactor
**Decision:** User records with their existing tool (OBS/Loom/QuickTime), then runs the finished file through PixelVeil.
**Why:** A live/real-time redaction extension would require competing with entrenched recording tools (OBS, Loom) for the recording step itself — high adoption friction for no benefit, since most target users won't switch recorders just for a blur feature. Post-processing meets users where they already are.
**Rejected alternative:** Chrome extension that records live and redacts during capture. Rejected because it only captures browser tabs (not full desktop), and asks users to change their entire recording workflow.

### D2 — Desktop app, not web app
**Decision:** Local Windows desktop app, all processing on-device.
**Why:** The product's core promise is privacy — "your recording never leaves your machine" is a stronger, more honest claim than "we promise to delete your upload after processing." A web app would make PixelVeil itself a server that (even briefly) stores other people's sensitive screen recordings, which contradicts its entire purpose.

### D3 — Windows only for v1
**Decision:** Target Windows exclusively, not cross-platform.
**Why:** Reduces build complexity significantly (single OS to test/package/support) and matches the primary target buyer's likely environment (QA/support teams on corporate Windows machines). Mac/Linux can be considered later if demand justifies it.

### D4 — Python as the core language
**Decision:** Build in Python, not Electron/Node or native C#/.NET.
**Why:** The two hardest technical problems — face detection and OCR — are Python-native ecosystems with the deepest documentation and best AI-coding-agent support of any language for these tasks. Building in Electron/Node or C# would mean either weaker library support or bridging out to a Python subprocess anyway, adding complexity for no benefit.

### D5 — MediaPipe over dlib/face_recognition for face detection
**Decision:** Use MediaPipe Face Detection.
**Why:** Pure pip install with prebuilt wheels — no CMake/Visual Studio Build Tools needed, which matters given an AI agent is doing much of the environment setup. Fast enough for frame-by-frame processing, good accuracy on frontal/near-frontal faces (the common case for screen recordings).
**Rejected alternative:** `dlib`/`face_recognition` — better documented in tutorials, slightly more accurate, but typically requires compiling from source on Windows unless an exact-matching prebuilt wheel is found. Real setup risk. Revisit for v2 if MediaPipe's accuracy proves insufficient in real testing.
**Also rejected:** OpenCV Haar Cascades (too many false negatives — unacceptable in a redaction tool), YOLO-face/RetinaFace (overkill weight for non-crowd screen recordings).

### D6 — Tesseract over EasyOCR/PaddleOCR for OCR (superseded — see D17)
**Original decision:** Use Tesseract via `pytesseract`.
**Why (at the time):** Fast enough on sampled frames, extremely well documented, free. Accepted cost: it's a separate binary that must be bundled at packaging time (known, well-documented step).
**Rejected alternative:** EasyOCR — no external binary, but PyTorch-based, meaning a much heavier dependency footprint and slower per-frame inference. Better on stylized/rotated text, but most on-screen text in the target use case (dashboards, CRMs) is clean and horizontal, so the extra weight isn't justified for v1.
**v2 note (historical):** add EasyOCR as an optional heavier/slower "high accuracy" mode if Tesseract's accuracy proved insufficient.
**Status:** Superseded by D17 (RapidOCR on ONNX Runtime) before the OCR detector was implemented. The "separate binary that must be bundled" cost this decision accepted is exactly what D17 removes. Kept here for history — the reasoning about clean/horizontal on-screen text and the pure-Python vs. external-binary tradeoff still informs D17.

### D7 — Regex over NER/ML for PII pattern matching
**Decision:** Use Python's built-in `re` module for email/phone/card/IP detection.
**Why:** These are structured, predictable formats — no ML model needed, no added dependency, no added failure mode. The cheapest and most reliable part of the pipeline; keep it that way.
**Deferred:** NER-based detection (spaCy/transformers) for unstructured PII like arbitrary names — not in v1 scope at all, so no need to carry the weight yet.

### D8 — OpenCV + ffmpeg mux, not MoviePy, for video I/O
**Decision:** Use OpenCV for frame read/write, ffmpeg for final audio muxing.
**Why:** OpenCV's own `VideoWriter` frequently produces poorly-compatible MP4s (codec issues, dropped audio). The reliable pattern is: process frames in OpenCV → write intermediate file → mux final output with original audio via ffmpeg.
**Rejected alternative:** MoviePy — convenient wrapper, but its abstraction layer makes the frame-by-frame pixel manipulation PixelVeil needs (drawing blur boxes) more awkward than working with OpenCV directly.

### D9 — Tkinter over PyQt for v1 GUI (superseded — see D10)
**Original decision:** Tkinter for the eventual product GUI — zero extra dependency, simplest for an AI agent to build against.
**Rejected alternative:** PyQt5/PySide6 — more polished, but PyQt5 has licensing complications for closed-source distribution (GPL/commercial license required); heavier dependency than needed for v1.
**Status:** Superseded for the *testing* phase by D10 (Flask/HTML test harness), but Tkinter (or CustomTkinter later) remains the plan for the actual shipped product GUI.

### D10 — Flask + local HTML test harness for development/testing
**Decision:** Build a local Flask-served HTML UI to run and observe the pipeline during development, instead of running scripts from the terminal repeatedly.
**Why:** Makes it far easier to visually inspect what each pipeline stage is doing (live frame preview with detection boxes, per-stage status, technical log) than parsing terminal output. This is a development/QA tool, not the final shipped product interface.

### D11 — PyInstaller over Nuitka for packaging (for now)
**Decision:** Use PyInstaller to build the distributable Windows `.exe`.
**Why:** Most standard, most documented tool for this, easiest for AI-agent-assisted debugging given wide community troubleshooting resources.
**Known accepted risk:** PyInstaller executables are commonly flagged by Windows Defender/antivirus as suspicious (the bundled-binary pattern resembles malware droppers). Mitigation (code signing or vendor allowlisting) is budgeted as a pre-launch task, not treated as a surprise blocker.
**Revisit trigger:** switch to Nuitka (compiles to actual C, less AV-flagging, better runtime performance, slower build iteration) if AV false-positives become a real adoption blocker closer to public launch.

### D12 — Freemium pricing model
**Decision:** Free tier (limited videos/length, blur mode only) + Pro tier ($12-15/mo, unlimited, fake-data mode, saved zone presets).
**Why:** Matches self-serve, no-sales-calls distribution goal; low enough price point for individual/small-team credit-card signup without procurement friction.

### D13 — Target buyer: QA/support teams, not general creators
**Decision:** Primary v1 marketing target is QA engineers and customer support teams recording bug-report/demo videos with real customer data on screen.
**Why:** This persona has proven willingness to pay for adjacent tools (e.g., BlurShot's screenshot tool explicitly targets QA/support), a clear recurring pain (dashboards/CRMs full of scrolling PII text, not just faces), and isn't the same crowded pool of YouTubers/journalists already well-served by existing face-blur-only tools.

### D14 — USP is PII text detection + fake-data replacement, not face blur
**Decision:** Lead all marketing with "we catch emails/phones/cards on screen, and replace them with realistic fake data" — face blur is included as table stakes, not the headline.
**Why:** Research confirmed face-blur-in-video is already commoditized (multiple free/open-source tools). No competitor found combines OCR-based PII detection with face blur on video, and none offer fake-data replacement (vs. blur/box only) for video. This is the actual unclaimed, defensible-enough ground.

### D15 — Child-only face detection deferred to v2, female/gender filtering dropped entirely
**Decision:** "Blur children only" mode is a defined v2 milestone, not v1. Gender-based face filtering is cut from scope permanently.
**Why:** Age-estimation accuracy is genuinely weak at the child/teen boundary — shipping this in v1 would risk a serious failure mode (an actual child left unblurred) before the base pipeline is even proven. When built in v2, the model must default to blurring on low confidence (over-blurring is acceptable; missing a child is not). Gender filtering was dropped because it adds real bias/accuracy risk with no clear safety justification, unlike the child-protection use case.

### D16 — Batch processing excluded from v1
**Decision:** Single file at a time only.
**Why:** Keeps v1 scope minimal and focused on proving the core detection pipeline works correctly before adding convenience features. Revisit once base product has paying users requesting it.

### D17 — RapidOCR on ONNX Runtime, replacing Tesseract (supersedes D6)
**Decision:** Use RapidOCR (the modern `rapidocr` package, v3.x) with the ONNX Runtime execution engine as the OCR backend. `core/ocr_detector.py` pins the det/cls/rec engines to `EngineType.ONNXRUNTIME`.
**Why:**
- **Fully offline, pure-pip, no separate binary.** The `rapidocr` wheel bundles its PP-OCRv6 detection/recognition ONNX models, so `pip install rapidocr onnxruntime` is the entire setup — no system Tesseract install, no PATH configuration, and nothing extra to bundle at packaging time. This removes the single accepted cost of D6 and the whole "install the Tesseract binary" / "bundle `assets/tesseract/`" workflow. Verified offline: models load from inside the installed package with no network access at runtime.
- **Good CPU performance for repeated frame OCR.** PixelVeil runs OCR repeatedly on sampled video frames (UI text, emails, phones, IPs, cards, terminal/browser text). RapidOCR's small ONNX models run efficiently on CPU-only Windows machines, which is the target environment (no GPU dependency, consistent with the rest of the pipeline).
- **Backend stays isolated.** The public contract `detect_text(frame) -> list[(text, bbox)]` is unchanged. All RapidOCR-specific handling (the `RapidOCROutput` result object, polygon corner arrays, `EngineType`) lives inside `core/ocr_detector.py`; `pii_matcher.py`, `redactor.py`, and `video_pipeline.py` only ever see the normalized `(text, (x, y, w, h))` list — the same axis-aligned integer-pixel bbox convention used by `face_detector.py`.
**Rejected alternatives (now):** `rapidocr_onnxruntime` (the older, separate 1.x/2.x package) — the modern unified `rapidocr` package with an explicit `EngineType.ONNXRUNTIME` selection supersedes it and is what is installed. PaddleOCR / EasyOCR — not revisited; adding a second/fallback OCR engine is explicitly out of scope for now.
**Installed versions at decision time:** `rapidocr` 3.9.2, `onnxruntime` 1.28.0 (bundled models: PP-OCRv6 det/rec small + PP-OCRv2 mobile cls).
**Carried forward from D6:** the observation that target on-screen text is clean and horizontal still holds; RapidOCR handles that case at least as well while dropping the external-binary cost. The bias remains "avoid missed PII over avoiding extra boxes" — the recognition confidence threshold is kept permissive (default 0.5) and pii_matcher.py, not the OCR stage, is responsible for rejecting non-PII text.

### D18 — Persist the generated fake-data string between OCR samples, not just the bbox
**Decision:** When OCR frame-sampling is active (`ocr_sample_rate > 1`), `core/video_pipeline.py` persists each PII region between samples as `(pii_type, bbox, replacement)` — where `replacement` is the fake-data string already produced by `utils.fake_data.generate()` at sample time — and reuses that same string on every intermediate frame until the next OCR sample. `fake_data.generate()` is therefore called once per detection (at the sample), not once per frame.
**Why:** `generate()` is randomized, so calling it per-frame on a persisted box would make the on-screen synthetic value change every frame (flicker) even though the underlying detection is one stable region. architecture.md §6.5/§7 introduce persistence specifically to avoid visual flicker and wasted computation between samples; persisting the *rendered value* (not only its position) is the direct extension of that rationale to fake-data mode. It also avoids redundant RNG work.
**Rejected alternative:** persist only `(pii_type, bbox)` and re-call `generate()` each frame — simpler state, but reintroduces the exact flicker the persistence design exists to prevent. **Scope note:** for the default `ocr_sample_rate=1` every frame is a sample, so `generate()` still runs each frame and behavior is identical to before this change — no observable difference in the every-frame path. Blur mode stores `replacement=None` (nothing to persist beyond the bbox).

### D19 — Convert display→original-video-pixel zone coordinates server-side, not in the browser
**Decision:** In the test-harness Upload screen (`tools/webtest/`), the browser sends each drawn zone as a **display-space** rectangle plus the canvas's current pixel size (`{rect:{x,y,w,h}, display:{w,h}}`); the Flask `/zone` route performs the display→**original-video-pixel** conversion via `upload_support.display_to_video_rect()` and stores the result as an `[x,y,w,h]` list in video pixels. The JS never computes or stores video-pixel coordinates.
**Why:**
- **The server is the single source of truth for the real video dimensions.** `ZoneManager.add_zone()` expects zones in original-video-pixel coordinates, not resized-canvas coordinates. The canvas is deliberately scaled to fit the single-column layout (`MAX_CANVAS_W=640`) and can be further CSS-scaled by the browser, so display coordinates are not the video's. Doing the conversion where the true `width`/`height` already live (in `_STATE`, set at upload from the decoded frame) means a resized, zoomed, or high-DPI canvas can never desync the mapping — the client only has to report *its own* current pixel size.
- **Testable without a browser.** The conversion is a pure function (`display_to_video_rect`) with per-axis independent scaling + clamping, unit-tested directly (identity, uniform 2×, non-uniform per-axis, edge clamp, zero-dim guard, full-frame resize roundtrip) and end-to-end through the `/zone` route with real videos — no headless-browser/JS harness needed.
- **Keeps the stored format directly consumable.** Because the server stores exactly what `ZoneManager` wants, the later pipeline-wiring task can hand `_STATE[uid]["zones"]` straight to `ZoneManager.add_zone()` with no re-mapping (proven by a test).
**Rejected alternative:** compute video-pixel coordinates in `app.js` and POST the already-converted rect. Rejected because it duplicates the video dimensions into client state (a second source of truth that can drift from the authoritative decode), buries the important mapping in untested browser JS, and would need a JS test harness to verify the resized-canvas case that the requirement explicitly calls out. **Scope note:** this governs only the Upload harness; it introduces no new dependency and does not touch `core/` (the conversion lives in `tools/webtest/upload_support.py`, which has zero Flask/`core` imports).

### D20 — Processing runs as one in-memory background thread, not a task queue
**Decision:** The test-harness Processing screen (`tools/webtest/`) runs `core.video_pipeline.process_video()` in a single daemon `threading.Thread` per job, with all live state (progress, cumulative face/PII counts, per-stage rows, technical log, summary/error) held in an in-memory `ProcessingJob` object (`tools/webtest/job.py`) guarded by a `threading.Lock`. The browser learns progress by polling `/job/<uid>` (~500 ms); the pipeline's own `progress_callback` (`{frame, total, faces, pii}`) plus its returned summary are the **only** sources of the displayed numbers. Exactly **one** job may be active at a time — a `/process` request while another job is running returns **HTTP 409**. Source (`uploads/`) and processed output (`outputs/`) live in separate directories.
**Why:** This is a single-user local QA tool (D10), not the shipped product. A daemon thread + polling is the smallest mechanism that keeps the request non-blocking and the UI live, adds **no** dependency, and needs no external service. Deriving every stage/log number strictly from the callback and summary (rather than inventing per-stage internals the pipeline can't report) keeps the debug console honest — a fabricated count would defeat the screen's entire purpose (design.md §2.2: watch what each stage is *actually* doing). The single-job invariant matches one operator watching one video and sidesteps concurrent-writer state entirely.
**Rejected alternative:** Celery/Redis, a database-backed job table, or a multi-worker queue. Rejected as gross over-engineering for a local single-user harness — real dependencies, setup, and failure modes for zero benefit here. Server-Sent Events was also considered for the log/progress stream (design.md §2.2 offers "SSE or polling") but polling was chosen for implementation simplicity and because it degrades trivially (a missed poll just retries); SSE remains a valid future swap behind the same `/job/<uid>` state. **Scope note:** governs only the Upload/Processing harness; `core/` is untouched and reached solely through `process_video()`'s existing public API.

### D21 — Serve preview JPEG via a dedicated endpoint, not embedded in the status poll
**Decision:** The Processing screen's live current-frame preview is a throttled, downscaled JPEG with detection boxes overlaid, generated by `tools/webtest/job.py` from the pipeline's new optional `preview_callback`. Only the **latest** preview is retained (never a growing frame buffer), and it is served through a dedicated endpoint `GET /job/<uid>/preview` — **never base64-encoded into the ~500 ms `/job/<uid>` status-poll JSON**. The status poll carries only lightweight signaling (`has_preview: bool`, `preview_seq: int`); when `preview_seq` changes the browser fetches the image separately with the seq as a cache-buster.
**Why:** A 480px-wide JPEG (the throttled diagnostic preview) is 10–50 KB. Base64-encoding that into every 500 ms poll would grow each poll response by ~15–70 KB and waste bandwidth/parse-time refreshing an image that changes far less frequently than progress numbers (the preview is throttled to every 6th processed frame by default, while the poll fires ~twice per second). Separating the image into its own endpoint lets the browser refresh it only when the seq changes, keeps the high-frequency status poll lightweight (pure JSON, <2 KB), and avoids parse overhead of extracting a large base64 string from JSON on every tick. The preview is purely diagnostic (drawn **after** the frame is written, so the overlay cannot affect the output video) — it doesn't need sub-second latency, and a separate fetch every ~3 seconds (at 10 fps, 6-frame throttle) is negligible overhead.
**Rejected alternative:** embed base64 JPEG in the poll JSON, or skip the preview image entirely. Base64 embedding rejected for the bandwidth/latency cost detailed above — the status poll is explicitly designed to be fast and frequent (design.md §2.2), and burdening it with 50 KB of rarely-changing image data defeats that. Skipping the preview rejected because the visual diagnostic (seeing the exact face/PII/zone boxes the pipeline drew) is a core Phase 3 deliverable and dramatically improves the harness's transparency over text logs alone. **Scope note:** the preview is test-harness-only observability (wired through an optional `preview_callback` added to `core/video_pipeline.py`); the pipeline's existing behavior, OCR sampling, audio mux, and summary are unchanged, and omitting the callback (as the shipped GUI will) costs zero overhead.

### D22 — Drop the Results "Flag an issue" in-app log; record misses in known-issues.md
**Decision:** The Results screen serves before/after video through **id-keyed controlled routes** (`/video/<uid>/original`, `/video/<uid>/processed`, `/download/<uid>`) that resolve paths from server-owned `_STATE`, never from a client-supplied filesystem path. The design.md "Flag an issue" button (a timestamped in-app miss log saved to a local file) is **not implemented** — manual misses found during review are written directly into `docs/known-issues.md` instead.
**Why:** This is a developer-only test harness, and the single developer already tracks issues by ID in `docs/known-issues.md` (per AGENTS.md §5). A second, in-app issue-logging channel (with its own storage format, API, and UI) would duplicate that workflow, add a write-to-disk API surface to the harness for no product value, and risk misses being split across two places. Serving videos through id-keyed routes (rather than a generic `send_file(path)` that takes a path argument) keeps the harness from ever exposing arbitrary filesystem reads, matching the "controlled routes" requirement.
**Rejected alternative:** implement the timestamped in-app log as originally speced. Rejected because it adds issue-report storage + an API endpoint + UI with no benefit over the existing `known-issues.md` process, and expands the harness's attack surface (a disk-writing endpoint) for a tool that is meant to stay minimal and offline. design.md §Screen-3 and testing.md updated to point at `known-issues.md`; the button is struck through in the spec so a later agent doesn't reintroduce it.

### D23 — Functional Settings via a process-local store + minimal core-API extensions
**Decision:** The Settings screen (OCR sample rate, face-detection confidence, four PII regex patterns) is made **functional** — a saved value actually changes what a subsequently started job does — through the smallest backward-compatible changes: (1) `core/pii_matcher.py` gains an active-patterns layer (`get_patterns`/`get_default_patterns`/`set_patterns`/`reset_patterns`) that the four `is_*()` functions consult, so overriding a pattern transparently changes the pipeline's PII classification; `set_patterns()` validates **all-or-nothing** (a bad regex or unknown type raises `ValueError` and leaves the active patterns untouched). (2) `core/video_pipeline.process_video()` gains an optional `face_min_confidence=None` param forwarded to the already-existing `face_detector.detect_faces(min_confidence=…)`; `None` preserves the detector's own default. (3) `core/face_detector.py` exposes `DEFAULT_MIN_CONFIDENCE` (public alias of the existing internal default). Settings themselves live in `tools/webtest/settings_store.py` — a **process-local, threading.Lock-guarded module dict**, reset on server restart; OCR rate + face confidence are read via `processing_kwargs()` when a job starts, and PII patterns are applied globally in `pii_matcher` at save time.
**Why:** The requirement is that a setting must affect real processing, not just render a control — but this is a local single-user QA harness (D10), so anything heavier than in-memory state is unwarranted. No database, user accounts, Redis, config service, or new dependency is added; restart-resets-to-defaults is the desired behavior for a test tool. The core extensions are deliberately additive and default-preserving: with no setting supplied every module behaves exactly as before (`face_min_confidence=None`, default patterns, `ocr_sample_rate=1`), so existing behavior and all prior tests are untouched. Applying PII patterns process-globally in `pii_matcher` (rather than threading them through `process_video` per call) means a newly started job automatically matches with the tuned patterns without widening the pipeline's signature, and it keeps all regex/matching logic in the module that owns it — Flask never duplicates detector/matcher/pipeline logic. All-or-nothing validation (in both `pii_matcher.set_patterns` and `settings_store.update_settings`) guarantees an invalid edit — bad OCR rate, out-of-range confidence, or uncompilable regex — is rejected with a 400 and never replaces the last valid configuration.
**Rejected alternative:** (a) persist settings to disk/config file/DB — rejected as out of scope for a single-user local harness that resets cleanly on restart (D10). (b) Thread PII patterns through `process_video(pii_patterns=…)` per call — rejected because it widens the core signature and duplicates the "which patterns are active" concept; the pattern-owning module (`pii_matcher`) is the right home for that state, and the pipeline already calls its `is_*()` functions. (c) Change the face detector's model/backend or add a new configurable detector — explicitly out of scope; only the already-exposed per-call `min_confidence` is surfaced. (d) Add new PII categories — out of scope for v1 (D7); the four types are fixed. Validated by `tests/test_webtest_settings.py`, `tests/test_pii_matcher.py::TestConfigurablePatterns`, and `tests/test_video_pipeline.py::TestFaceMinConfidence`; all tests restore process-global settings in tearDown so state cannot leak across files.

### D24 — Fake-data mode: classical inpainting + heuristic source-style estimation, not solid-fill or generative reconstruction
**Decision:** Deliver the D14 USP (fake-data replacement) by making `fake_data_region` **style-aware** and **background-reconstructing** instead of the previous flat solid-white-fill + fixed black-on-white text. Three additive pieces in `core/redactor.py`, orchestrated by `core/video_pipeline.py`:
1. `estimate_text_style(frame, bbox)` — called on each PII value's bbox **before** the pixels are destroyed. Estimates foreground/text colour and background colour with k-means (`k=2`, minority cluster = ink), and glyph height by Otsu-thresholding then tracing external contours (with a **minority-polarity** normalization so the ink, not the fill, is what's measured). Returns a style dict (`text_color`, `bg_color`, `text_height`, `baseline_offset`, `width`) or `None`.
2. `inpaint_region(frame, mask, method)` — removes the original value by OpenCV `cv2.inpaint`, method `"telea"` **or** `"ns"` (Navier-Stokes), radius 3. **Both methods are kept selectable via `process_video(inpaint_method="telea")`; no single winner is chosen** — they are for manual quality comparison.
3. `fake_data_region(frame, bbox, text, inpaint_method=None, style=None)` — inpaints (or solid-fills when `inpaint_method` is None) then draws the replacement in the estimated fg colour on the reconstructed bg, sized to the estimated glyph height (`FONT_HERSHEY_SIMPLEX` cap ≈ `height/22`, then width-fitted). The pipeline persists `(pii_type, value_bbox, replacement, style)` so the style, like the value, survives between OCR samples (extends D18).
**Why:**
- **The USP is *replacement*, not a censor bar (D14).** A flat white box with fixed black text ignores the source entirely — a bright-green-on-dark value became black-on-white, and the box read as an obvious redaction rather than a plausible substitution. Estimating colour/height from the source and reconstructing the background makes the substituted value sit in the surrounding UI far more naturally.
- **Classical inpainting only — stay local/offline/CPU (D1/D4 spirit).** TELEA and Navier-Stokes ship inside OpenCV, add **no dependency**, and run fast on CPU. They cleanly reconstruct the flat/near-flat panels typical of screen UIs. No GAN/diffusion/LaMa/STE — those are explicitly out of scope (heavy, often GPU, and overkill for the target content).
- **Estimate before destroy.** Style must be read before removal, so the pipeline computes it in the sample branch (alongside `fake_data.generate()`) and persists it; the redaction pass consumes the persisted style. This is the direct extension of D18's "persist the rendered value" to "persist the rendered *style*."
- **Both inpainting methods retained deliberately.** TELEA and NS produce subtly different fills; which looks better is content-dependent and a human judgement. The parameter is surfaced (default `"telea"`) and both remain available rather than hard-coding one.
**Explicitly NOT claimed / NOT attempted:** this is an **approximation, not reconstruction**. Colour and height are heuristics that can misfire; the replacement is always the Hershey font, **not** the source font (no font-family identification or reconstruction is attempted); inpainting can smear on textured backgrounds; and at `ocr_sample_rate=1` the randomized value regenerates per frame (flicker). The output is **not** described as "seamless" — it is a plausible, clearly-synthetic substitution. See ISSUE-007 for the full limitation list.
**Two genuine defects fixed while landing this (not behavior changes — bug fixes):** (1) `estimate_text_style` originally chose contour polarity by comparing cluster-centre brightness, which traced the **background** blob and collapsed `text_height` to the full box height; replaced with the polarity-agnostic minority-pixel rule. (2) Replacement scale used `target_height/40`, ~40% too small for Hershey's real cap height; corrected to `target_height/22` (measured via `cv2.getTextSize`), width-fit still only shrinks.
**Rejected alternatives:** (a) **Keep solid-fill + fixed black-on-white** — simplest, but defeats the D14 USP (obvious censor bar, ignores source appearance). (b) **Generative/deep inpainting (LaMa, diffusion, GAN, scene-text editors)** — best visual quality but violates the local/offline/CPU/no-heavy-ML constraints, adds large dependencies/models, and is unjustified for flat-UI backgrounds. (c) **Pick one inpainting method** — rejected for v1; both are cheap to keep and the choice is a human quality call left open. (d) **Exact font reconstruction** (font identification + matched rendering) — out of scope; heavy and unnecessary for a clearly-synthetic replacement. **Scope note:** additive and backward-compatible — calling `fake_data_region` without `style`/`inpaint_method` reproduces the old solid-fill + black-text path, so nothing outside fake_data mode changes. Validated by `tests/test_fake_data_quality.py` (`26 passed`), `tests/test_redactor.py` (`14 passed`), `tests/test_video_pipeline.py::TestFakeDataStylePersistence`, and real-video renders on `tests/sample_videos/test_mixed.mp4` (both methods).

### D25 — Harness processes fake_data twice (TELEA + NS) for manual comparison; blur unchanged
**Decision:** In the **test harness only** (`tools/webtest`, a dev/QA tool — D10), a job in **fake_data** mode runs `core.video_pipeline.process_video()` **twice, sequentially** — once with `inpaint_method="telea"`, once with `"ns"` — writing one output file per method (`<stem>_telea.mp4` / `<stem>_ns.mp4`) so a developer can eyeball both classical-inpainting fills side by side. **Blur mode is untouched and still runs exactly once.** The dual run is driven by an optional `compare_methods` list passed into `ProcessingJob` (a list of `(label, inpaint_method, output_path)`); with it absent the job runs a single pass exactly as before. The core pipeline, redaction logic, and both inpainting implementations are **not** modified — this only calls the existing public API twice with a different `inpaint_method`.
- **One job, two passes.** `ProcessingJob` presents the two runs to the UI as ONE job: overall progress spans both passes (TELEA fills 0–50%, NS 50–100% via `_percent_locked` = `(pass_index + frame/total) / num_passes`); the job reaches COMPLETE **only after both** succeed; frame/face/PII counters reset per pass so the twice-processed input is **not** double-counted.
- **Controlled error state names the method.** If either pass raises, the whole job enters ERROR (never a false success) with `failed_method` set and a message naming the method (`"TELEA pass failed — …"` / `"NS pass failed — …"`). A single-pass (blur / plain) job re-raises the original error unchanged.
- **Summary shown once; discrepancy flagged not hidden.** Inpainting changes pixels, not detections, so both passes must report identical frames/faces/PII/zones. The Results summary is rendered **once** from the first pass; `_check_summary_discrepancy()` compares the two detection views and, if they differ, sets `summary_discrepancy` (surfaced on Results + logged) rather than silently trusting one.
- **Server-owned paths only (D22 security model preserved).** fake_data jobs store `output_paths = {"telea": …, "ns": …}` (and drop the single `output_path`); the new routes `/video/<uid>/telea|ns` and `/download/<uid>/telea|ns|both` resolve files **only** from that server-owned state keyed by a fixed method allowlist — never from client input. Unknown id, incomplete job, wrong mode (blur → per-method routes 404), and missing file all return controlled 404/409, never filesystem access. "Download Both" is an in-memory ZIP built with the **stdlib `zipfile`** (no new dependency) containing exactly the two outputs under their method-specific basenames.
**Why:** D24 deliberately left **both** TELEA and NS available and chose no winner, because which looks better is content-dependent and a human judgement on real recordings. The harness is exactly where that human comparison happens, and doing both in one job (rather than making the developer run twice, rename files, and juggle outputs) is the low-friction way to get a fair, same-input A/B. Keeping it in the harness (not the core pipeline or the eventual GUI) matches D10 — this is a QA affordance, not a shipped feature.
**Explicitly temporary / no winner chosen here.** This is a comparison capability, not a decision about TELEA vs NS. The fake-data quality algorithms (OCR/PII detection, style estimation, fake-value generation, the inpainting implementations themselves, face detection, zones, H.264/audio) are unchanged so the comparison is fair. When the developer picks a default from eyeballing the outputs, that will be a **separate** decision; this entry only records the mechanism.
**Rejected alternatives:** (a) **Ask the user to pick a method before processing** — defeats the purpose (you can't compare what you didn't render) and adds a settings knob for a throwaway QA step. (b) **Process once and swap the fill in post** — impossible without re-running detection/redaction; the inpaint is inside the per-frame pass. (c) **Put the dual-run in `process_video()`** — pollutes the core public API with a QA concern and would double-count/complicate its single-summary contract; the harness owning the two sequential calls keeps core semantics clean. (d) **Overwrite one output / reuse one filename** — loses the very thing being compared. (e) **A new dependency for the ZIP** (e.g. an archive lib) — unnecessary; stdlib `zipfile` into `io.BytesIO` suffices. **Scope note:** additive and backward-compatible — `ProcessingJob` without `compare_methods` and a blur `/process` are byte-identical to before (verified: the single-run forwarding contract is still tested via blur). Validated by `tests/test_webtest_dual_output.py` (`28 passed`) + the unchanged webtest suites; full suite `290 passed, 100 subtests`.
